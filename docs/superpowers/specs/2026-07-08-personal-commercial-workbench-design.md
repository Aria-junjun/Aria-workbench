# AI 辅助的个人商业操作与知识资产工作台需求文档

## 1. 结论

本产品定位为一个云端可访问的个人商业操作与知识资产工作台。第一阶段以供应链场景为落地重点，帮助用户把供应商沟通、货盘信息、产品知识和待办事项从截图、聊天记录、口述文字等碎片信息中低成本沉淀下来。

第一阶段不做企业 ERP、订单管理、库存管理、财务结算、复杂审批或团队协作。系统的核心价值不是让用户手动维护表格，而是通过 AI 辅助整理和确认页，降低记录成本，并逐步形成可查询、可追溯、可复用的个人商业资产。

## 2. 背景与问题

用户从事供应链相关工作，经常需要在 1688 等平台筛选和沟通供应商。过去大量信息依赖记忆，包括供应商基本情况、沟通历史、报价条件、货盘差异、产品原材料、工艺、成本构成和经验判断。

当前主要问题：

- 供应商沟通结果没有稳定沉淀，后续容易忘记或重复沟通。
- 货盘信息分散在截图、聊天记录、链接和个人记忆中，难以长期复用。
- 产品知识在调研后没有形成结构化资料，无法逐步积累成品类资产。
- 待办事项依赖临时记忆，容易漏跟进样品、报价、交期、复盘等事项。
- 商业知识、读书笔记和业务判断没有和实际业务对象建立关联。
- 用户不擅长也不喜欢逐字段填写，因此传统表格方案容易失败。

## 3. 产品目标

### 3.1 第一阶段目标

第一阶段目标是跑通供应链场景的核心闭环：

供应商 -> 沟通记录 -> 货盘归档 -> 产品知识 -> 待办提醒

具体目标：

- 用户可以通过截图、聊天记录粘贴、口述文字三种方式快速录入信息。
- AI 自动提取供应商、沟通内容、货盘、产品知识和待办草稿。
- 所有 AI 提取结果进入确认页，由用户确认后再入库。
- 供应商、货盘、产品知识、待办可以被查询、筛选和关联。
- 为后续客户、商机、竞品、项目、读书笔记等业务扩展保留底层结构。

### 3.2 非目标

第一阶段暂不包含：

- 订单管理
- 库存管理
- 财务结算
- 采购审批流
- 多角色权限
- 团队协作
- 大规模自动爬取 1688 数据
- AI 自动替用户做最终供应商决策
- 复杂货盘对比

## 4. 核心用户原则

用户不是缺少表格工具，而是缺少低摩擦的信息沉淀机制。因此产品设计必须遵循：

- 少手填：优先支持截图、粘贴、口述。
- 先确认再入库：AI 只生成草稿，不直接污染正式数据。
- 前台具体：第一版界面围绕供应链场景，不展示过度抽象的对象系统。
- 底层通用：数据模型支持未来扩展到其他商业对象。
- 先沉淀，再智能：第一阶段先保证可查、可追溯、可复用，后续再做推荐和判断。

## 5. 第一阶段模块

### 5.1 快速录入入口

用途：提供统一入口，让用户用最低成本提交碎片信息。

支持输入：

- 上传沟通截图
- 粘贴聊天记录
- 输入口述总结
- 添加 1688 商品或供应商链接
- 上传货盘图片或资料

录入后，系统将信息交给 AI 整理流程，生成结构化草稿。

### 5.2 AI 整理确认页

用途：承接 AI 提取结果，避免错误信息直接进入正式库。

确认页展示：

- 识别到的供应商
- 本次沟通摘要
- 新增或更新的供应商信息
- 识别到的货盘信息
- 识别到的产品知识
- 自动生成的待办事项
- AI 标注的不确定字段和风险点

用户操作：

- 确认入库
- 修改字段
- 删除误识别内容
- 合并到已有供应商或产品
- 标记为待补充

### 5.3 供应商库

用途：沉淀所有沟通过的供应商及其历史表现。

核心字段：

- 供应商名称
- 1688 链接
- 主营品类
- 所在地区
- 联系人
- 联系方式
- 工厂或贸易商
- 供应能力
- 配合度
- 价格水平
- 质量判断
- 风险标签
- 综合备注
- 最近沟通时间
- 下次跟进时间

供应商详情页应展示：

- 基础信息
- 沟通记录时间线
- 关联货盘
- 关联产品知识
- 待办事项
- 用户判断和风险备注

### 5.4 沟通记录库

用途：保存每次供应商沟通的过程和结果。

核心字段：

- 关联供应商
- 关联货盘或产品
- 沟通日期
- 信息来源：截图、聊天记录、口述、链接
- 沟通摘要
- 报价变化
- 供应商承诺
- 用户疑点
- 风险提示
- 下一步动作
- 原始附件

沟通记录是供应商画像的主要依据。

### 5.5 货盘库

用途：归档供应商提供过的产品和交易条件。

第一阶段只做整理归档，不做复杂对比。

核心字段：

- 货盘名称
- 关联供应商
- 产品品类
- 图片或附件
- 1688 链接
- 报价
- MOQ
- 交期
- 规格参数
- 包装信息
- 样品情况
- 适合渠道
- 优势说明
- 风险或疑点
- 备注

### 5.6 产品知识库

用途：沉淀用户对产品、品类、工艺和成本的理解。

核心字段：

- 产品或品类名称
- 原材料
- 工艺流程
- 成本构成
- 关键参数
- 质量风险
- 常见坑点
- 替代方案
- 相关供应商
- 相关货盘
- 资料来源
- 用户判断

产品知识应支持从沟通记录和口述总结中不断补充。

### 5.7 待办提醒

用途：从沟通记录中自动生成跟进事项，减少遗忘。

核心字段：

- 待办标题
- 关联供应商
- 关联货盘或产品
- 截止时间
- 优先级
- 状态
- 来源沟通记录
- 提醒类型
- 完成备注

常见提醒类型：

- 确认报价
- 跟进样品
- 确认 MOQ
- 确认交期
- 补充产品工艺信息
- 复盘供应商
- 再次沟通

### 5.8 商业知识和读书笔记

用途：轻量沉淀供应链之外的商业认知资产。

第一阶段做轻量版，不与供应链主流程争夺复杂度。

核心字段：

- 标题
- 来源：书籍、文章、课程、沟通、观察
- 主题标签
- 摘要
- 关键观点
- 可应用场景
- 关联供应链问题
- 行动启发

## 6. 自动化能力规划

### 6.1 第一阶段自动化

第一阶段自动化重点是 AI 辅助整理，不追求完全自动执行。

内置自动化流程：

1. 供应商沟通整理
   - 输入：截图、聊天记录、口述文字
   - 输出：供应商更新、沟通记录、待办草稿

2. 货盘归档
   - 输入：货盘截图、链接、聊天片段、口述文字
   - 输出：货盘草稿和关联供应商

3. 产品知识沉淀
   - 输入：原材料、工艺、成本、风险点等碎片信息
   - 输出：产品知识页草稿

4. 商业知识沉淀
   - 输入：读书笔记、商业观点、案例
   - 输出：标准化知识条目

### 6.2 Skill 自动化

系统后续应支持将高频流程沉淀为可复用 Skill。

第一批 Skill：

- 供应商沟通整理 Skill
- 货盘归档 Skill
- 产品知识沉淀 Skill
- 商业知识沉淀 Skill

Skill 的职责是将重复流程标准化，例如：

- 识别输入类型
- 提取关键字段
- 判断应更新哪个库
- 生成草稿
- 标注不确定信息
- 生成待办建议

Skill 不应在未经确认的情况下直接做最终判断或覆盖重要数据。

## 7. 底层扩展模型

第一版前台围绕供应链，但底层应采用可扩展结构。

通用模型：

- 对象 Object：供应商、客户、竞品、产品、项目、渠道、书籍、人物
- 记录 Record：沟通记录、调研记录、报价记录、会议记录、观察记录
- 资产 Asset：货盘、商机、产品知识、方案知识、商业观点、读书笔记
- 任务 Task：跟进、提醒、确认、复盘、样品、报价、行动建议
- 关系 Relation：对象、记录、资产和任务之间的关联
- 附件 Attachment：截图、图片、链接、文件
- 标签 Tag：品类、风险、优先级、状态、业务线

后续扩展路径：

- 客户 -> 沟通记录 -> 商机 -> 方案知识 -> 待办
- 竞品 -> 调研记录 -> 产品卖点 -> 风险判断 -> 行动建议
- 读书笔记 -> 商业观点 -> 关联供应链问题 -> 行动启发

设计原则是底层通用、界面具体，避免第一版变成难用的抽象系统。

## 8. 推荐建设阶段

### 阶段 1：MVP 基础工作台

目标：先让用户开始沉淀信息。

包含：

- 登录
- 首页工作台
- 快速录入
- 供应商库
- 沟通记录库
- 货盘库
- 产品知识库
- 待办提醒
- 商业知识轻量库
- 基础搜索和筛选

### 阶段 2：AI 辅助录入

目标：减少用户手填。

包含：

- 截图上传识别
- 聊天记录粘贴整理
- 口述文字整理
- AI 字段提取
- AI 不确定项标注
- 确认页
- 自动生成待办草稿

### 阶段 3：Skill 自动化

目标：把高频动作固化成可复用流程。

包含：

- 供应商沟通整理 Skill
- 货盘归档 Skill
- 产品知识沉淀 Skill
- 商业知识沉淀 Skill

### 阶段 4：业务扩展

目标：从供应链工作台升级为个人商业操作与知识资产工作台。

可扩展模块：

- 客户库
- 商机库
- 竞品库
- 项目库
- 渠道库
- 方案知识库

## 9. 技术方向建议

第一版建议采用 Web 应用方式建设，支持账号登录和云端访问。

基本能力：

- 前端 Web 界面
- 后端 API
- 云端数据库
- 文件和图片存储
- 用户认证
- AI 结构化提取接口
- 定时提醒任务

技术选择的重点不是复杂度，而是：

- 容易快速迭代
- 数据可导出
- 适合结构化关系数据
- 支持图片和附件
- 后续方便接入 AI 和自动化流程

## 10. 主要风险

### 10.1 字段过多导致用户不愿使用

应对：第一版字段只保留关键项，其他信息进入备注或后续补充。

### 10.2 AI 提取错误污染数据

应对：所有 AI 结果必须经过确认页，不直接入库。

### 10.3 第一版过度抽象

应对：界面聚焦供应链，不展示复杂的通用对象系统。

### 10.4 自动化过早复杂化

应对：先稳定数据结构和确认流程，再沉淀 Skill。

### 10.5 变成大而全企业系统

应对：明确不做订单、库存、财务、审批和多人权限。

## 11. 成功标准

第一阶段成功标准：

- 用户能在沟通后用截图、粘贴或口述完成一次低摩擦记录。
- 系统能生成可确认的供应商沟通草稿。
- 用户确认后，信息能正确进入供应商、沟通记录、货盘、产品知识和待办。
- 用户能通过供应商或产品查到历史沟通和相关货盘。
- 用户能看到下一步待办，减少遗漏。
- 使用体验不要求用户像维护表格一样逐字段填写。

## 12. 待确认事项

以下事项应在实施计划阶段进一步确认：

- 第一版是否使用邮箱、手机号或第三方账号登录。
- 图片 OCR 和 AI 提取使用哪个服务。
- 待办提醒第一版采用站内提醒、邮件、短信还是微信/企业微信。
- 是否需要支持手机端优先体验。
- 第一版部署方式和预算范围。
- 数据备份和导出格式。
