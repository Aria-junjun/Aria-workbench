# 工作台人工云端备份设计（2026-10-08）

## 目标与边界

将当前浏览器的工作台业务快照可靠备份到既有 Supabase 项目，并在本机数据丢失时可核验地恢复。默认采用人工同步；保留未来启用自动同步的代码入口，但自动上传和定时拉取均关闭。工作台仍管理过程、依据和责任，聚水潭仍是采购交易结果的权威来源。本设计不把本地侧边栏代码发布误称为数据同步，也不补造南翊家居的订单事实。

现有 `workbench_data` 云端快照与 2026-10-08 重新导出的本地主要业务记录均为 66 个产品、46 家供应商、11 条采购记录、33 条供应商业务记录和 93 条月度入仓记录。原先 11 个产品的备份是在项目恢复前生成，不作为写入依据。实施前保留最新业务 JSON，并只读重核云端快照。

## 同步契约

1. `manual` 是默认模式。页面启动时使用本机快照，不定时读写云端；本机业务保存只写本机并标记“待备份”。保留 `auto` 开关，但其将来启用时也必须走同一版本校验写入路径，不能恢复无条件整份覆盖。
2. 页面持续显示“仅本地／待备份／云端已核验／冲突待处理／连接失败”之一及最后成功核验时间。“云端已核验”仅在上传成功且回读核对通过后出现；网络失败时不得显示成功。
3. “备份到云端”先只读取得云端行 `id、updated_at、data`，展示各集合本机与云端的记录数量、增删改摘要和可能影响。已有本机基准版本时，云端版本与基准不同即停止；首次建立基准时，仅在标准化后的业务快照等价时自动建立，不等价则停止并供导出两端快照。用户确认后才上传。
4. 服务端对整份快照写入要求提交客户端所见的 `updated_at`；数据库更新必须带该版本条件，更新 0 行返回冲突。缺少版本的旧客户端整份写入请求一律拒绝。不得把冲突伪装成普通网络失败，也不得自动按字段或订单行拼接。
5. 上传成功后重新读取云端，按稳定 ID 和标准化内容核对整份主快照；核验通过才清除本机待备份标记并记录云端版本。回读不一致时保留本机数据及待处理状态。
6. “从云端恢复”是独立动作：先下载当前本机业务 JSON，预览云端与本机差异，再二次确认覆盖。本机尚有待备份修改时默认阻止恢复；除非用户明确选择保留导出的本机副本并确认放弃该浏览器内的未备份改动。

## 数据与权限安全

- 不删除现有云端行、历史业务记录或用户文件。先检验最新本机 JSON 可解析；发布前后核对云端主记录数量、稳定 ID 和关键样例。
- 云端页面当前仍是旧版代码；在新保护逻辑发布并验证之前，不让旧版自动同步与新本地页面并行写同一快照。
- `public.workbench_data` 的 RLS 告警单独审查。确认现有访问均由已认证的服务端代理执行后，再以拒绝匿名直连为目标设计策略；不能直接因安全告警而执行未经验证的 SQL，或让正常恢复路径中断。
- 浏览器 JSON 备份仅覆盖统一主快照。产品导入草稿、附件和其他独立存储应在发布检查中单列，不得声称主快照已代表所有数据。

## 页面与服务边界

- `data-sync-loader`（或拆出的同步状态组件）：显示状态、差异预览与两个方向的人工动作；无自动定时器和焦点触发写入。
- `local-store`：本机业务保存、待备份标记、云端基准版本、人工上传及回读核验；失败时保持本机数据。
- `supabase-proxy`：提供带版本的只读快照和条件写入，拒绝无版本的旧写入及并发冲突。
- 云端业务快照仍为原有单行结构；本阶段不新增 ERP 订单、财务分摊或自动合并规则。

## 验收与发布门槛

1. 测试覆盖：打开页面及保存业务时零自动云端写入；手动上传成功后回读一致；断网、旧版本、首次不等价、并发更新和恢复取消均不覆盖本机或云端数据；未来 `auto` 模式也不得绕过版本保护。
2. 当前本地基线有 10 个失败测试、1 个测试文件无法加载、类型检查失败。先区分过期断言与真实缺陷并修复发布阻断，再运行全量测试、类型检查和独立构建。任何残留失败都明示，不以局部测试代替全量通过。
3. 本地分支有大量未提交和未跟踪改动，发布前逐项审查纳入范围、备份和回退路径；只把经验证的代码发布到 Vercel。发布后在云端验证新导航、人工同步状态和原有业务记录，另行确认数据库访问权限。

## 不在本阶段

不自动合并冲突订单，不按数量差推断质量或交期，不补造南翊家居采购单号/承诺日期，不开启总监审批，不将“网页可打开”视为云端备份成功。
