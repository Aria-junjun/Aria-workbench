# 代发周期履约决策闭环设计

## 目标

让已导入的代发周期数据进入供应商管理总览和待建档处理流程，形成“看见异常—判断样本—执行处理—追溯档案”的最小闭环。保留现有采购和供应商页面结构。

## 数据口径

- 正式周期履约来自 `supplierBusinessRecords` 中的 `dropship_period` 记录。
- 未关联商家来自 `pendingDropshipSuppliers`，商品事实来自 `dropshipProductPeriods`。
- 同一平台、周期、供应商只保留一条当前记录，重复导入覆盖该周期。
- 订单量少于 20 为样本不足，仅观察；20–99 为建议建档；100 及以上可进入绩效判断。
- 低样本异常只提示，不进入正式绩效排名。

## 管理总览

新增“代发经营监控”区块，读取正式周期履约和待建档数据，展示：

- 最新统计周期、周期订单量、GMV、加权 48H 揽收率、加权退款率。
- 可评价供应商数、风险供应商数、待建档数、样本不足数。
- 风险行动队列：供应商、订单量、核心异常、建议动作、进入档案入口。
- 待建档行动队列入口，跳转到供应商业务台账的代发周期页。

风险沿用现有规则：48H 揽收率低于 95%、签收时长超过 72 小时、退款/售后率超过 10%、拒退率超过 10%、3 分钟响应率低于 70%。高订单量且存在异常时标记高量高风险。

## 待建档处理

每条待建档商家提供四类动作：

1. 关联已有供应商档案：生成正式周期履约记录，并从待建档区移除。
2. 新建供应商档案：以来源商家名称创建基础档案，写入周期履约，再移除待建档记录。
3. 继续观察：保留记录并写入处理状态，适用于样本不足。
4. 存档：保留历史证据但退出当前待处理队列，适用于产品下架或停止合作。

列表必须显示系统建议及依据，并提供状态筛选；任何动作完成后立即刷新统计。

## 边界与风险

- 本阶段不接入 1688 API，不自动推断公司全称与店铺简称的关系。
- 不自动建立正式供应商，不自动做淘汰决定。
- 管理总览只反映已导入数据，明确展示统计周期与样本门槛。
- 不涉及付款、账期和财务结算。

## 验收

- 导入并确认数据后，管理总览能看到代发指标和风险队列。
- 待建档记录可完成关联、新建、观察、存档，并实时影响待办数量。
- 样本不足记录不进入正式风险排名。
- 处理后的履约数据能在对应供应商档案中追溯。
- 相关领域测试、界面测试和 TypeScript 检查通过。
