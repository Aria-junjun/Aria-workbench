# Aria 工作台交付治理与复盘基线

日期：2026-08-25  
适用范围：入仓产品、货盘报价、供应方案、供应商决策；一件代发和机会产品暂不纳入本阶段经营闭环

## 1. 是否需要 PRD、技术栈、测试用例和项目进度

需要，但不建议分别写成互相脱节的大文档。建议采用“一个领域模型 + 四个轻量交付附件”的方式：

- 领域模型：定义业务对象、术语、关系和边界。
- PRD：定义用户要完成的决策、输入、输出和验收标准。
- 技术说明：定义数据来源、存储、导入、同步和不变量。
- 测试矩阵：定义业务口径、关键流程、异常和回归用例。
- 进度台账：定义阶段、完成证据、风险、下一步和是否同步云端。

领域模型是上位约束；PRD 和技术方案不能改变业务关系，只能实现它。

## 2. 当前技术基线

### 已使用

- Next.js App Router 15
- React 19
- TypeScript 5
- Tailwind CSS
- Supabase Auth/Postgres/Storage，用于云端登录、数据/备份和存储能力
- 本地工作台快照与云端同步机制
- Zod，用于输入校验
- `xlsx`，用于 Excel 导入
- Vitest / Testing Library / Playwright，用于领域、UI 和端到端验证
- OpenAI 兼容结构化提取接口，用于低摩擦录入草稿

### 技术原则

1. **来源优先。** 原始文件和导入批次保留，结构化数据只是可追溯的解析结果。
2. **确认后入正式关系。** AI 建议、相似匹配和导入异常先进入预览/待确认区。
3. **快照不可静默覆盖。** 同一对象、同一月份、同一口径重复导入时必须提示替换。
4. **空值不等于零。** 空白字段显示“未采集/待填写”，只有明确的 0 才保存为 0。
5. **决策可回放。** 产品和供应商结论必须保存周期、来源、理由和后续动作。
6. **聚水潭不复制。** 工作台只存对决策有用的月度事实和证据，不复制订单明细和 ERP 全量台账。

## 3. PRD 最小模板

每个新功能只需要回答以下问题：

1. 决策问题：用户要据此做什么决定？
2. 业务对象：影响产品族、SKU、货盘、供应商还是待办？
3. 数据来源：聚水潭导出、供应商文件、沟通记录还是人工确认？
4. 统计周期：月度、周度还是事件发生时？为什么？
5. 输出动作：只是展示、产生决策，还是生成待办？
6. 缺失处理：没有数据时显示什么，是否允许判断？
7. 追溯方式：能否定位月份、文件、工作表、导入批次和确认人？
8. 验收标准：如何证明功能真的改变了决策，而不只是多了一个数字？

当前优先 PRD：

- `P-01` 入仓产品族月度经营决策
- `P-02` SKU—货盘—供应商实际供应关系
- `P-03` 供应商事实与协同决策
- `P-04` 产品/供应商决策证据与待办
- `P-05` 供应链驾驶舱（仅汇总前四项，不新增录入）

## 4. 测试矩阵

### 领域规则

- 产品族能正确汇总多个 SKU。
- 月度实发、退货数量和退货率口径正确：退货率 = 实退数量 / 实发数量；无实发时不得计算。
- ERP 成本基准只作为参考，不被误称为财务利润。
- `Y-02BBT-8` 等组合 SKU 不会错误地覆盖基础 SKU。
- 货盘规格确认与实际供应商选择是两个独立状态。
- 部分 SKU 未匹配时，不自动生成“供应商覆盖不足”的供应商结论。
- 没有供应商证据时评分显示“未采集”，不显示默认 A/100。

### 导入与数据安全

- 只写入可匹配的内部 SKU；未匹配行留在预览区。
- 空白和明确 0 的行为不同。
- 同 SKU、同月份重复导入必须提示替换。
- 历史月份不会被当前月份覆盖。
- 原始报价和原始文件信息不丢失。
- 本地保存、云端同步和刷新后读取结果一致。

### 页面流程

- 产品族展开后，主表列与 SKU 明细列完全对齐。
- 供应商名称、货盘、SKU 和产品跳转到正确对象。
- 供应商决策按钮能生成决策记录，完成后状态和历史可见。
- 只有可执行动作生成待办；普通缺失字段不制造噪音。
- 详情页没有数据时显示明确空状态，而不是空白或假数据。

### 发布前最低门槛

- 领域测试通过
- 关键页面 UI 测试通过
- `npx tsc --noEmit` 通过
- `npm run build` 通过
- `/product-master`、`/offers`、`/suppliers` 和关键详情页返回 200
- 本地与云端抽查同一数据、同一月份、同一状态

## 5. 当前进度台账

| 工作流 | 当前状态 | 已有证据 | 主要缺口 |
|---|---|---|---|
| 产品机会/入仓产品分层 | 已落地基础 | `recordKind`、产品模式、SKU 生成入仓产品 | 产品决策历史需统一 |
| SKU 主表与产品族 | 已落地基础 | Excel 导入、产品族聚合、展开明细 | 组合 SKU 组成关系需进入汇总 |
| 货盘报价与比价 | 已落地 | 列表、卡片、SKU 比价、供应商视图、详情 | 供应关系需与货盘关系继续拆开 |
| 规格对应关系 | 已落地基础 | 确认、撤销、保存 | 批量确认后的影响范围需更清晰 |
| 月度经营数据 | 已落地基础 | 月度快照、实发/退货/ERP 成本 | 产品汰换规则和历史结论需统一 |
| 月度实际入仓 | 已落地基础 | 导入和供应商关联 | 供应商有效期和更换历史需强化 |
| 供应商决策总览 | 已落地基础 | 实际供货、动作、证据和决策历史 | 评分模型仍需降级并归一 |
| 供应商详情/协同 | 已落地基础 | 决策动作、历史、货盘 | 质量/交付事件的低频入口需补齐 |
| 待办 | 已有能力 | 截止日期、状态、关联对象 | 由决策缺口生成并回写对象 |
| 导入导出/业务档案 | 规划中 | 原始数据和备份能力 | 合同、报价、决策包的版本化导出 |
| 供应链驾驶舱 | 尚未正式建设 | 已有可汇总数据 | 不应在数据不足时先做大屏 |

## 6. 建议的后续里程碑

### M1：统一数据关系

冻结领域模型、字段字典、数据来源和状态机；补齐产品族、SKU、实际供应关系的显示与编辑边界。

### M2：产品经营决策

把月度经营数据转成可解释的产品决策记录，保留用户已有的产品汰换标准，不在空数据时下结论。

### M3：供应商事实闭环

把实际供货、报价条件、质量信号、协同事件和主备关系串成供应商决策；评分只做有证据时的辅助汇总。

### M4：证据、待办和导出

将“缺什么”与“下一步谁做什么”连接起来，并支持产品决策包、供应商档案包和完整备份导出。

### M5：供应链驾驶舱

只呈现已经存在且能驱动动作的指标：产品需要关注什么、供应商需要采取什么动作、证据是否完整、下次复核何时发生。

## 7. 复盘节奏

- 每次功能完成：记录对象、来源、口径、测试和云端同步状态。
- 每月业务复盘：导入经营/入仓数据，确认产品决策和供应商动作。
- 每季度模型复盘：检查指标是否真的影响决策，删除无动作的数据字段。
- 每次发现数据异常：先检查对象关系和来源，不先改展示文案。

## 8. 本阶段不建议做的事

- 现在就做复杂供应链大屏。
- 为了“看起来完整”补齐库存、利润、服务分等无法稳定采集的字段。
- 把聚水潭已有的采购执行和库存功能搬进工作台。
- 用一个综合分数替代产品决策和供应商决策。
- 在没有确认实际供应关系前，把退货率直接写到供应商头上。
